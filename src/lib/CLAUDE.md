# src/lib
Purpose: server business logic shared by browser routes, integration routes, server.ts timers and pages; plus a few client helpers. Overview: [docs/architecture.md](../../docs/architecture.md).

## Files
- Core: mongodb.ts (cached connection), redis.ts (optional), config.ts (env getters), logger.ts (pino), crypto.ts (AES-256-GCM field encryption, plus `encryptBytes`/`decryptBytes` for receipt images).
- Auth: auth-options.ts, auth-guard.ts (`requireAuth`), cron-auth.ts, security-rate-limit.ts (atomic counting, safe under concurrent callers), log-security.ts, log-auth-request.ts, device-label.ts, email.ts.
- Money services: account-service.ts, transaction-service.ts, transfer-service.ts (transfers between own accounts: create, edit, delete over transaction-service), cash-service.ts (the cash account: low-cash view, setup on demand; `findCashAccount` is in account-service.ts), transaction-query.ts, transaction-activity.ts, stats-service.ts (month, range and daily totals), notification-service.ts, budget-service.ts, budget-alert.ts, spend-limit.ts (daily and weekly limit status, alerts and the end-of-day summary; a change to the amounts applies from today and is kept in `limitHistory`, `limitOn(history, current, date)` gives the limit a past day had; its zod schema lives in features/budgets/schemas/spend-limit.schema.ts), spend-limit-time.ts (day and week bounds in the user's time zone; `localDate` and `localDateKey` give the wall-clock date), goal-service.ts, loan-service.ts, credit-card-service.ts (summary and statements read paths), credit-card.ts, credit-balance.ts, card-rewards.ts (pure: reward rule schema, per-transaction rounding down, cap, refund take-back) and card-rewards-service.ts (rule get, set, clear and the per billing cycle estimate; shared by browser and integration routes), rule-service.ts (categorise rules: CRUD, first-match evaluation, the overrides applied on a new transaction), ledger.ts.
- Household sharing: share-service.ts (owner invites an email with chosen accounts, a role (viewer or editor) and optional budgets; the one-time invite code is hashed (sha256, constant-time compare, single use, 7 days); `loadActiveShare(memberId, ownerId)` is the ONLY access check, every shared read and the editor write call it first and a miss is a uniform 404; reads are whitelisted fields over the owner's shared, live, non-archived accounts only, transfers hide an unshared side; an editor adds one plain income or expense through the owner's `createTransaction` with the member as ledger actor and `Transaction.addedBy`; `revokeAllSharesOfUser` runs on account deletion), share-browser.ts (JSON errors for the `/api/household` routes) and integrations/share-http.ts (integration errors, the Idempotency-Key plumbing; the one-time code is added to the first answer only and never stored in the idempotency record). Design and threat model: [docs/household.md](../../docs/household.md).
- Tags, splits and receipts: tags.ts (`tagListSchema` normalises user tags and rejects link tags with a colon; `mergeUserTags` keeps the server's link tags on an edit), split-service.ts (`getSplit`, `replaceSplits`: edit the lines of a split or turn a plain expense into one; same total, no balance change), receipt-service.ts (receipt photos encrypted in the `receipts` collection, ids in `Transaction.attachments`; limits, magic-byte type check, `preflightReceipt` (everything refusable without the image, run before the body is read), `readReceiptBody` (byte cap, 30 s total, 10 s idle and a 20 KB/s floor after 3 s, one read per person, 16 per process), `receiptImageHeaders`; shared by browser and integration routes).
- Tax: tax-year.ts (pure: financial year April to March named by its start year, bounds at the user's midnight), tax-settings.ts (`preferences.tax.deductibleCategories`, `categoryKey`, atomic diff) and tax-service.ts (`getTaxSummary` one grouped aggregation, `foldTaxGroups` pure, CSV rows, `setTransactionDeductible`); shared by browser and integration routes.
- spend-limit-time.ts `localMidnight` returns the first real instant of a day where a clock change skips midnight (Santiago, Beirut); where midnight happens twice (Amman, Havana) it is the first of the two, and for a day a zone skipped altogether (Samoa, 2011-12-30) it is the next day's start; every day window, the weekly review and the CSV import and export use it.
- Multi-currency: currency.ts (pure: supported codes, minor-unit digits, `convertMinor` is the one place a foreign amount becomes base paise), exchange-rate-service.ts (open.er-api.com, one cached table per base in `exchange_rates`, 24 hour refresh, 30 day stale fallback, client `rate` override) and base-currency.ts (`preferences.currency`; `lockBaseCurrency` is called before every write of a base-unit amount and sets `users.baseLocked` atomically, `setBaseCurrency` only changes it while nothing is locked or stored). Display currency for any base-unit amount is the base, never an account's `currency` label. `transaction-service` `resolveAmount` applies them on create. Only a two-decimal currency can be the base for now (`isSupportedAsBase`, error `UNSUPPORTED_BASE_CURRENCY`): `setBaseCurrency` refuses others and `resolveAmount` rejects writes for a stored base that is not two-decimal. Code that reads `minorExponent(base)` (export, import, tax, money-format) is harmless but a non-2 base is not selectable yet.
- Net worth: net-worth.ts (assets minus liabilities from accounts, cards, loans and manual assets; a stored point per user per local day for the trend; manual asset CRUD; `recordSnapshotsForAllUsers` for the cron).
- Subscriptions: subscription-detector.ts (pure: finds repeating merchant charges, cadence, next date, yearly cost) and subscription-service.ts (reads 24 months of expenses, merges the user's confirm and dismiss decisions; shared by browser and integration routes).
- Export and import: csv-import.ts (pure: RFC 4180 parser, header guess, date and amount cells to paise, one row to a candidate; caps 1 MB, 500 rows, 50 columns; comma only as thousands grouping; a row's date is local midnight in the user's zone), transaction-import.ts (`previewImport` dry run and `commitImport` over the same analysis; duplicates = same account, user-clock day, type, amount, counted so equal rows in a file match only as many as exist), transaction-export.ts (CSV with 20,000 row cap). Both work in minor units of the base currency (`getBaseCurrency`, `minorExponent`: yen 0, rupee 2, dinar 3), never the account label; commit calls `lockBaseCurrency` before the first insert. Imported rows are source `import`; `createTransaction` takes server-only `skipBalance` and skips alerts, round-up and categorise rules for that source. One import per account at a time (`ImportLock`, unique doc with TTL); no `dateOrder` on a file with ambiguous dates is a 400 on commit. `withIdempotency` takes `pendingTtlSeconds` for long writes; `readJsonBodyLimited` (integrations/write-helpers.ts) counts bytes as read.
- Forecast: forecast-math.ts (pure: daily balance points, lowest point, shortfall, subscription repeats) and cash-flow-forecast.ts (gathers liquid balances, unpaid recurring items, card and loan dues from bills.ts, subscriptions and the 30 day average spend).
- Bills: bills.ts (upcoming bills from recurring payments, card statements and loans owed; mark paid), bill-settings.ts (`preferences.billReminders`), bill-reminders.ts (once per bill per due date, from 09:00 local; `sendBillReminders`).
- Sinking funds and savings rate: sinking-fund-service.ts (funds with a due date and monthly set-aside; `describeFund` computes remaining, percent, monthsLeft, suggestedMonthly and status on read; atomic contribute) and savings-rate.ts (income minus spending per month from `getRangeStats`, average and trend). integrations/write-helpers.ts holds the Idempotency-Key, JSON body and conflict-message checks new integration routes share.
- Backup: backup-crypto.ts (passphrase to AES-256-GCM file: scrypt N=2^17 for version 2, version 1 files still open, header bound as AAD, one generic failure, size caps, a gate of two key derivations with a short queue, taken by `withKeyGate` before any database work; waiters give up after 10 s, a job after 50 s) and backup-service.ts (`buildBackup` whitelist export, zod schemas, `restoreBackup` merge-only with a dry run; payload version 2 carries baseCurrency (a file in another base is refused once money data exists, otherwise the base is set and locked via base-currency.ts, and only when something is written; a version 1 file has no base and only restores into an INR account; transactions must carry the file's base and rows are relabelled with it; the foreign-amount group is validated all-or-none), foreign originals, the tax flag and deductible categories; receipts and the server's link tags are not restored, caller owns every row, HMAC-derived (subkey of CAPTURE_ENCRYPTION_KEY via `deriveSubkey` in crypto.ts) per-person ids for ids held by others, rehashed with an attempt number if taken, so a re-run is a no-op and the id cannot be squatted, series and split group ids remapped when another person uses them). Format and threat model: [docs/backup.md](../../docs/backup.md); the HTTP side is integrations/backup-http.ts.
- Weekly review: weekly-review.ts (`summarizeWeek` and `buildHighlights` are pure; `getWeeklyReview` reads one Monday to Sunday week in the user's time zone; `sendWeeklyReviews` is the opt-in notification) and weekly-review-settings.ts (`preferences.weeklyReview`).
- Recurring and reminders: recurrence.ts, recurring-topup.ts, recurring-series.ts (series list, get, cancel; shared by browser and integration routes), reminder-scheduler.ts, emi-notifications.ts, credit-notifications.ts, push.ts.
- refund-service.ts (match a credit to the expense it refunds, suggest, confirm, reject; stats and budgets net confirmed refunds out), see [docs/reconcile.md](../../docs/reconcile.md).
- capture/ (ingest, parsers, source priority, account matching), reconcile/ (correct, inbox, http): [docs/reconcile.md](../../docs/reconcile.md).
- capture/ingest.ts: an ATM withdrawal parse (`atm: true` from `parseCapture`) with a live cash account is created as a transfer to cash, not an expense; `handleMatch` never rewrites that transfer from a later message.
- integrations/ (API-key auth, handler, idempotency, rate-limit, response, sms-parser), app-update.ts: [docs/n8n-integration.md](../../docs/n8n-integration.md).

## Rules and gotchas
- Household sharing never changes how an existing query is scoped: every current route still filters by `user`. New shared reads must go through `loadActiveShare` and the share's account ids, return a field whitelist (never the raw document), and answer 404, not 403, for anything the caller may not see; a share is never cached. No realtime resource streams shared data. `createTransaction` skips the owner's goal round-up for a row with `provenance.addedBy` (a household editor's); the editor write re-reads the live share right before it writes.
- budget-service and goal-service own create, update and soft delete; the browser `[id]` routes and the integration `[id]` routes both call them.
- transfer-service owns transfer edit (amount, accounts, date: balances fixed in one pass); create and delete call transaction-service. A transfer row is never income or spending.
- subscription-service never stores detections, only the user's choice per merchant and cadence (`SubscriptionDecision`); it leaves out recurring series the user already tracks (`isRecurring`).
- tax-service answers `currency` and `exponent` (the base currency, `minorExponent`), writes CSV amounts with `minorToMajor` under an `amount (CODE)` header, and the `/tax` page formats with money-format.ts `formatMinor` (utils.ts `formatCurrency` assumes 2 decimals). It sums only the stored base `amount`, never `originalAmount`; a split line is its own row and counts once.
- tax-service counts income and spending only: no transfers (an ATM withdrawal is one only with a cash account), voided or deleted rows, recurring instalments once paid. A confirmed refund comes off spending in the year it arrived (cash basis, the refund's own date), is skipped when its original is voided or deleted, and is deductible as its original is (this user's expenses read by id in chunks of 1000 after the year's refunds are grouped, no `$lookup`). Known limit: a refund links to one split line, so for a split purchase deductibility comes from that line only, not the whole group. Category names are compared with `categoryKey` in JS on both sides, never Mongo `$toLower` (ASCII only). `availableYears` reads only the first and last rows (`yearRangeReads`; `isDeleted` matched as `$in [false, null]` so the date indexes give the order; the first and last `date` over all counted rows plus the first and last `paidAt`, so the list never misses a year but may offer one with no counted row when a scheduled date is far from the paid date). Refund groups are never cut short. Settings change by `changeTaxCategories` (atomic add and remove, 50 name cap). csv.ts leaves a real number alone, so a negative amount stays numeric, while text starting with a formula character is quoted.
- A confirmed refund (`refundStatus: confirmed` income row) is netted out in stats-service, budget-service and budget-alert; a new aggregation over income or expense must do the same.
- rule-service owns categorise rules; createTransaction() and capture/ingest.ts call it, the browser and integration rule routes call it. Rules are not a realtime resource.
- loan-service owns loan create, update, delete and repayments; the browser and integration loan routes both call it.
- Put logic here, not in routes. transaction-service, loan-service, goal-service, budget-service and stats-service exist so web and integration routes cannot drift.
- No mongoose sessions anywhere; multi-step writes are sequential.
- `appendLedgerBlock` (ledger.ts) writes a per-user hash chain (`sequence`, `previousHash`, `hash`); concurrent appends retry up to 25 times on the unique {user, sequence} index.
- Redis and the TTL caches are optional or per instance; code must work without them.
- A split is one Transaction row per line, so stats and budgets need no split logic; keep it that way. Only split lines through split-service/createTransaction.
- split-service edits the lines in ONE Mongo transaction (`session.withTransaction`; production is a replica set, tests use `MongoMemoryReplSet`): rows, new rows and receipt moves commit or abort together, two edits at once serialise on the first line (write conflict, retried), ledger blocks are written after the commit. Receipts of removed lines move to the first line (cap checked in the same update) before the line is deleted. Other code stays free of sessions.
- Receipt cascade (`deleteReceiptsOfTransactions`) runs AFTER the delete/void/cancel, retries once, then logs; `getReceiptImage` checks the parent, quota counts only live parents, and `sweepOrphanReceipts` (on list and add) purges leftovers. Account self-delete purges receipts as its last step; `/api/me/export` lists their metadata only.
- Receipts: never return a receipt URL or bytes without `getReceiptImage(userId, id)`; a receipt is deleted with its transaction (`deleteReceiptsOfTransaction` in `deleteTransaction`). The key is `CAPTURE_ENCRYPTION_KEY` with the purpose `receipt`: changing that env value makes stored receipts unreadable.
- capture/ingest.ts reads `CAPTURE_ENCRYPTION_KEY`; log-security.ts reads `TOTP_ENCRYPTION_KEY`.
- integrations/sms-parser.ts (`parseBankSms`) has no importer in src, scripts or server.ts; ingest uses `parseCapture` from capture/parsers.
