# src/lib
Purpose: server business logic shared by browser routes, integration routes, server.ts timers and pages; plus a few client helpers. Overview: [docs/architecture.md](../../docs/architecture.md).

## Files
- Core: mongodb.ts (cached connection), redis.ts (optional), config.ts (env getters), logger.ts (pino), crypto.ts (AES-256-GCM field encryption, plus `encryptBytes`/`decryptBytes` for receipt images).
- Auth: auth-options.ts, auth-guard.ts (`requireAuth`), cron-auth.ts, security-rate-limit.ts (atomic counting, safe under concurrent callers), log-security.ts, log-auth-request.ts, device-label.ts, email.ts.
- Money services: account-service.ts, transaction-service.ts, transfer-service.ts (transfers between own accounts: create, edit, delete over transaction-service), cash-service.ts (the cash account: low-cash view, setup on demand; `findCashAccount` is in account-service.ts), transaction-query.ts, transaction-activity.ts, stats-service.ts (month, range and daily totals), notification-service.ts, budget-service.ts, budget-alert.ts, spend-limit.ts (daily and weekly limit status, alerts and the end-of-day summary; a change to the amounts applies from today and is kept in `limitHistory`, `limitOn(history, current, date)` gives the limit a past day had; its zod schema lives in features/budgets/schemas/spend-limit.schema.ts), spend-limit-time.ts (day and week bounds in the user's time zone; `localDate` and `localDateKey` give the wall-clock date), goal-service.ts, loan-service.ts, credit-card-service.ts (summary and statements read paths), credit-card.ts, credit-balance.ts, card-rewards.ts (pure: reward rule schema, per-transaction rounding down, cap, refund take-back) and card-rewards-service.ts (rule get, set, clear and the per billing cycle estimate; shared by browser and integration routes), rule-service.ts (categorise rules: CRUD, first-match evaluation, the overrides applied on a new transaction), ledger.ts.
- Household sharing: share-service.ts (owner invites an email with chosen accounts, a role (viewer or editor) and optional budgets; the one-time invite code is hashed (sha256, constant-time compare, single use, 7 days); `loadActiveShare(memberId, ownerId)` is the ONLY access check, every shared read and the editor write call it first and a miss is a uniform 404; reads are whitelisted fields over the owner's shared, live, non-archived accounts only, transfers hide an unshared side; an editor adds one plain income or expense through the owner's `createTransaction` with the member as ledger actor and `Transaction.addedBy`; `revokeAllSharesOfUser` runs on account deletion), share-browser.ts (JSON errors for the `/api/household` routes) and integrations/share-http.ts (integration errors, the Idempotency-Key plumbing; the one-time code is added to the first answer only and never stored in the idempotency record). Design and threat model: [docs/household.md](../../docs/household.md).
- Tags, splits and receipts: tags.ts (`tagListSchema` normalises user tags and rejects link tags with a colon; `mergeUserTags` keeps the server's link tags on an edit), split-service.ts (`getSplit`, `replaceSplits`: edit the lines of a split or turn a plain expense into one; same total, no balance change), receipt-service.ts (receipt photos encrypted in the `receipts` collection, ids in `Transaction.attachments`; limits, magic-byte type check, `preflightReceipt` (everything refusable without the image, run before the body is read), `readReceiptBody` (byte cap, 30 s total, 10 s idle and a 20 KB/s floor after 3 s, one read per person, 16 per process), `receiptImageHeaders`; shared by browser and integration routes).
- Anomaly alerts: anomaly-rules.ts (pure: the three rules and their constants, `largeSpend`, `duplicateOf`, `categoryJump`), anomaly-settings.ts (`preferences.anomalies`: on by default, muted categories compared with `categoryKey`, atomic add and remove, 50 name cap) and anomaly-service.ts (`detectAnomalies` runs in the background after `createTransaction` and never throws; `raise` creates the `Anomaly` once per cause (unique dedupKey) and then its notification and push; `listAnomalies`, `resolveAnomaly` (report tags the expense `anomaly-reported` through transaction-service `addUserTag`, ledgered and refused on loan or statement linked rows; no answer ever removes the tag, the person does; a failed inbox notification keeps the alert and a failing check does not stop the others; the duplicate lookup reads at most 50 rows in the window), `retireAnomaliesForTransactions` called from `deleteTransaction`, which voiding goes through, also for the other half of a duplicate pair; spending is read by category exactly as stored, mute matches any case). Not checked: income, transfers, recurring rows, imports, voided or deleted rows; a split line only gets the category jump. Shared by browser and integration routes.
- Tax: tax-year.ts (pure: financial year April to March named by its start year, bounds at the user's midnight), tax-settings.ts (`preferences.tax.deductibleCategories`, `categoryKey`, atomic diff) and tax-service.ts (`getTaxSummary` one grouped aggregation, `foldTaxGroups` pure, CSV rows, `setTransactionDeductible`); shared by browser and integration routes.
- spend-limit-time.ts `localMidnight` returns the first real instant of a day where a clock change skips midnight (Santiago, Beirut); where midnight happens twice (Amman, Havana) it is the first of the two, and for a day a zone skipped altogether (Samoa, 2011-12-30) it is the next day's start; every day window, the weekly review and the CSV import and export use it.
- Multi-currency: currency.ts (pure: supported codes, minor-unit digits, `convertMinor` is the one place a foreign amount becomes base paise), exchange-rate-service.ts (open.er-api.com, one cached table per base in `exchange_rates`, 24 hour refresh, 30 day stale fallback, client `rate` override) and base-currency.ts (`preferences.currency`; `lockBaseCurrency` is called before every write of a base-unit amount and sets `users.baseLocked` atomically, `setBaseCurrency` only changes it while nothing is locked or stored). Display currency for any base-unit amount is the base, never an account's `currency` label. `transaction-service` `resolveAmount` applies them on create. Only a two-decimal currency can be the base for now (`isSupportedAsBase`, error `UNSUPPORTED_BASE_CURRENCY`): `setBaseCurrency` refuses others and `resolveAmount` rejects writes for a stored base that is not two-decimal. Code that reads `minorExponent(base)` (export, import, tax, money-format) is harmless but a non-2 base is not selectable yet.
- Net worth: net-worth.ts (assets minus liabilities from accounts, cards, loans, manual assets and holdings; a stored point per user per local day for the trend; manual asset CRUD; `recordSnapshotsForAllUsers` for the cron).
- Subscriptions: subscription-detector.ts (pure: finds repeating merchant charges, cadence, next date, yearly cost) and subscription-service.ts (reads 24 months of expenses, merges the user's confirm and dismiss decisions; shared by browser and integration routes).
- Export and import: csv-import.ts (pure: RFC 4180 parser, header guess, date and amount cells to paise, one row to a candidate; caps 1 MB, 500 rows, 50 columns; comma only as thousands grouping; a row's date is local midnight in the user's zone), transaction-import.ts (`previewImport` dry run and `commitImport` over the same analysis; duplicates = same account, user-clock day, type, amount, counted so equal rows in a file match only as many as exist), transaction-export.ts (CSV with 20,000 row cap). Both work in minor units of the base currency (`getBaseCurrency`, `minorExponent`: yen 0, rupee 2, dinar 3), never the account label; commit calls `lockBaseCurrency` before the first insert. Imported rows are source `import`; `createTransaction` takes server-only `skipBalance` and skips alerts, round-up and categorise rules for that source. One import per account at a time (`ImportLock`, unique doc with TTL); no `dateOrder` on a file with ambiguous dates is a 400 on commit. `withIdempotency` takes `pendingTtlSeconds` for long writes; `readJsonBodyLimited` (integrations/write-helpers.ts) counts bytes as read.
- Forecast: forecast-math.ts (pure: daily balance points, lowest point, shortfall, subscription repeats) and cash-flow-forecast.ts (gathers liquid balances, unpaid recurring items, card and loan dues from bills.ts, subscriptions and the 30 day average spend).
- Bills: bills.ts (upcoming bills from recurring payments, card statements and loans owed; mark paid), bill-settings.ts (`preferences.billReminders`), bill-reminders.ts (once per bill per due date, from 09:00 local; `sendBillReminders`).
- Envelopes: envelope-service.ts (envelope mode: `getEnvelopePlan`, `assignEnvelopes`, `moveBetweenEnvelopes`, `copyEnvelopePlan`; a month is ONE `EnvelopePlan` document changed by atomic single-document updates, a pipeline update with the cap in its filter for assign and a conditional `$inc` with array filters for a move, so no transaction is needed; a move cannot take more than the source has assigned, nor below what it had spent at that moment (spend is read just before the update); `spent` comes from budget-service `spentByCategory`; amounts are base paise, a non-two-decimal base is refused and the first amount locks the base), envelope-browser.ts (shared shape of the browser write routes; an optional Idempotency-Key header makes a write run once per key and a replay returns the stored answer, a refusal included, so retry a refused write with a new key). Guarantees: every service write ends in `viewAfterWrite`, so a read-back failure after the commit answers a `partial: true` view (`partial` is false otherwise) instead of an error; the one write call of assign, move and copy runs inside `uncertainOnError`, and an error from it (timeout, dropped acknowledgement) becomes `EnvelopeWriteUncertain`, which `withIdempotency`'s `keepPendingOn` keeps pending, so the route answers 409 `IDEMPOTENCY_CONFLICT` (check the plan) and no retry under that key can run the write again; no `pendingTtlSeconds`, so a pending key is blocked for the idempotency TTL and the person (or app) starts over with a new key after checking the plan; only failures proven to happen before the write drop the pending record. The web keeps one key per exact move in a module store (features/envelopes/lib/move-key.ts), settled by the mutation. `canonicalJson` in integrations/write-helpers.ts is the deep fingerprint body for a route whose body has a list of objects (`withIdempotency` fingerprints top-level keys only).
- Holdings: holding-math.ts (pure, BigInt: decimals, price times units, gain percent, SIP due dates counted from the start month, fixed deposit simple interest) and holding-service.ts (list with totals and upcoming SIPs, create, update, archive, record a manual value with a 100 entry history; at most 500 per person; locks the base and refuses a non-two-decimal base). net-worth.ts counts live holdings as one asset row `holdings`.
- Sinking funds and savings rate: sinking-fund-service.ts (funds with a due date and monthly set-aside; `describeFund` computes remaining, percent, monthsLeft, suggestedMonthly and status on read; atomic contribute) and savings-rate.ts (income minus spending per month from `getRangeStats`, average and trend). integrations/write-helpers.ts holds the Idempotency-Key, JSON body and conflict-message checks new integration routes share.
- Backup: backup-crypto.ts (passphrase to AES-256-GCM file: scrypt N=2^17 for version 2, version 1 files still open, header bound as AAD, one generic failure, size caps, a gate of two key derivations with a short queue, taken by `withKeyGate` before any database work; waiters give up after 10 s, a job after 50 s) and backup-service.ts (`buildBackup` whitelist export, zod schemas, `restoreBackup` merge-only with a dry run; payload version 2 carries baseCurrency (a file in another base is refused once money data exists, otherwise the base is set and locked via base-currency.ts, and only when something is written; a version 1 file has no base and only restores into an INR account; transactions must carry the file's base and rows are relabelled with it; the foreign-amount group is validated all-or-none), foreign originals, the tax flag and deductible categories; receipts and the server's link tags are not restored, caller owns every row, HMAC-derived (subkey of CAPTURE_ENCRYPTION_KEY via `deriveSubkey` in crypto.ts) per-person ids for ids held by others, rehashed with an attempt number if taken, so a re-run is a no-op and the id cannot be squatted, series and split group ids remapped when another person uses them). Format and threat model: [docs/backup.md](../../docs/backup.md); the HTTP side is integrations/backup-http.ts.
- Bank link (Account Aggregator, framework only, [docs/account-aggregator.md](../../docs/account-aggregator.md)): aa-service.ts (consents: start, refresh, map, revoke; `syncConsent` bounded by page, count and time; `syncNow` with a cooldown; `syncAllConsents` for the cron and timer with a run guard (it first runs `retryPendingWithdrawals`: consents flagged `withdrawPending` by `purgeAaRecordsOfDeletedUser` are withdrawn at the provider and deleted only after it confirms; they are never listed or synced); `deleteAaDataForUser`), aa/ (provider.ts the `AaProvider` seam, providers.ts the registry picked by `AA_PROVIDER` (unset = off), sandbox.ts the in-memory fake with `sandboxControl` for tests) and `ingestAaTransaction` in capture/ingest.ts (channel `aa`, priority 2, one captured message per provider transaction id, matched against captures and then against unlinked manual rows; history older than the link is written with `provenance.historical` and `skipBalance`, which skip balance, alerts and round-up but not rules; the capture keeps `historical` so `resolveCapture` in reconcile/inbox.ts does the same; aa/provider.ts also holds the zod schemas every provider answer passes through; account-service `archiveAccount` clears bank link mappings and claims for the account; AaAccountClaim is the atomic one-feed-per-account guard; every provider call has a timeout (`PROVIDER_TIMEOUT`); the sandbox is refused in production without `AA_ALLOW_SANDBOX`; `createTransaction` (single and split) writes the row(s) and the balance move(s) in ONE database transaction (`inOneTransaction`, a replica set) so a crash leaves both or neither, with ledger blocks after the commit; it marks `skipBalance` rows `balanceApplied: false`, which delete, void, `correctTransaction`, `updateTransfer`, split clones and the recalculate sums honour, so a history transfer (`skipBalance`) leaves the destination account alone too. Its ledger blocks are written after the commit and a failure there is logged, not thrown, and not repaired automatically (`appendLedgerAfterCommit`; single, split and series creates), so a retry cannot double-book. `updateTransfer` still applies its balance deltas account by account (separate writes), a known limit. The recalculate route and a recurring series cancel write an absolute balance from a sum (read, then save): a create that lands in between is overwritten, a known limit of those two).
- Weekly review: weekly-review.ts (`summarizeWeek` and `buildHighlights` are pure; `getWeeklyReview` reads one Monday to Sunday week in the user's time zone; `sendWeeklyReviews` is the opt-in notification) and weekly-review-settings.ts (`preferences.weeklyReview`).
- Recurring and reminders: recurrence.ts, recurring-topup.ts, recurring-series.ts (series list, get, cancel; shared by browser and integration routes), reminder-scheduler.ts, emi-notifications.ts, credit-notifications.ts, push.ts.
- refund-service.ts (match a credit to the expense it refunds, suggest, confirm, reject; stats and budgets net confirmed refunds out), see [docs/reconcile.md](../../docs/reconcile.md).
- capture/ (ingest, parsers, source priority, account matching), reconcile/ (correct, inbox, http): [docs/reconcile.md](../../docs/reconcile.md).
- capture/parsers layout (ticket 153): `index.ts` NFKC-normalises the text (styled Unicode letters read as plain, for every sender), then the OTP check, then `notices.ts` (mandate notices and fund-house notes, ticket 157), then the rest of `ignore.ts` (reminder, failed, promo), then `formats.ts` (exact shapes: Navi EMI, IDFC card spend, any sender), then the sender's bank parser from `registry.ts` (`BANK_PARSERS`, picked by the SMS header with the `VM-` prefix and `-S` suffix removed (`sender.ts`), or for a notification by its app package only, never its label), then `generic.ts`. A bank parser extends `BankParser` (`base.ts`): it lists `senderIds` and `packageNames` and overrides only the steps that differ (amount, direction, cardPayment, account, paidCard, date, merchant, ref, atm); `parse` returning null means "not mine" and the generic parser still runs, so anything never to be booked goes in `ignore.ts`; the shared caps (foreign currency 0.6, card bill payment 0.5) stay in the base. Shared rules live in `extract/`. `createCaptureParser(parsers)` builds a parse over a given list for tests. Ingest passes `sender` and `packageName`. - capture/parsers notices (ticket 157, parser version 6): `notices.ts` runs right after the OTP check, before the other ignore checks. The rule is "when in doubt it is money": a message is a notice only with a positive notice shape AND nothing saying money moved, because a wrongly kept notice loses a payment without a trace while a missed one only costs a Review item. `parseMandateNotice` (kind `mandate`: event, merchant, max amount, frequency, last4, start and end dates; never the UMN, UMRN, a PAN or a reference-like UPI id) needs the event verb in the mandate's own clause (mandate word and event at most 100 characters apart, no sentence end, so "Balance updated." after a NACH credit is not a mandate update) and, when in doubt, a mandate message goes to Review (money), never dropped. It may print an amount only as the mandate's limit (`onlyLimitAmounts`: right after max, maximum, up to, limit, not exceeding or ceiling, or "modified/changed/revised/increased/reduced to"; an unlabelled amount, even "AutoPay of Rs 449 to X confirmed", is money (review round 5); amounts are read as widely as findAmount: Rs, Re, INR, ₹, foreign codes and symbols, Amt or Amount, bare decimals like 449.00; any other amount, an amount within 30 characters of an account or card mask, or a "transaction of" an amount means money moved, which a verb list can never cover: recovered, pulled, realised, billed, ka bhugtan), is vetoed by a money noun (`MONEY_NOUN`: success (not "registration success"), payment (not "payments will", "next payment on", "no further payments"), recovery, deduction, collection, instalment, EMI, kisht, ran, gone, hit; "first/next EMI on <date>" is allowed), by any account or card mask in the clause holding an amount, by any past-tense word that is not a mandate event or a neutral word (`unknownPast`: confirmed, expired, signed, submitted, ended, increased, extended and "registration ... completed" are neutral; renewed and a bare completed are not; recovered, honoured, cleared, renewed, vasool, ho gaya, jama; "will be debited" and the future wording "can now auto-debit up to", "next debit as per schedule" are allowed), and by any money word (`moneyMoved`: DEBIT_WORDS, CREDIT_WORDS, debit, Dr, Cr, executed, processed, done, paid, used, WDL, txn, deposited, received, sent, "successful" unless it is "successfully created/registered/..." or "created/registered/... successfully"); a request, a failure or a pre-debit notice stays with ignore.ts. `parseInvestment` (kind `investment`: fund, amount, units and NAV as printed strings, last 4 of the folio only; the fund name never holds a folio, PAN, amount or account) needs a fund house's own words (folio, NAV, units allotted, mutual fund, AMC; a bare "fund" as in "Relief Fund" or "fund transfer" is not enough), a fund event and a done word, and is vetoed by any money word ("purchase" only counts as money when no folio, NAV or units are printed), by the person's account or card digits (a folio mask aside), by collected, remitted, paid out, jama or credited back, by a failed, due, IPO, refund or advertised SIP, and whenever the sender is a bank with a parser (a bank's message about a SIP or a redemption is the money itself). Ingest stores both as `outcome: ignored` with reason `mandate` or `investment`, never a transaction, never in Review. Money into a loan ("loan account XX6618 is credited ... by debit to A/c XX7305", "credited to your loan account") is an expense of the account it left (`findDirection`), sure of the account only when the message says it was debited ("by NACH debit from your HDFC Bank A/c" counts); a disbursal or a loan amount transferred to your account keeps the usual reading, and so do interest, cashback, subvention or a subsidy unless the message names an EMI, repayment or prepayment or the debited account ("EMI incl. interest ... by debit to Acct" is a repayment); interest, cashback, subvention or a subsidy as the subject of its own "credited" sentence ("Interest subsidy of Rs 1,140 credited ...") is never a repayment. A merchant is never the bare word "debit" or "NACH debit", and a mandate debit's merchant drops a leading "e-mandate", "NACH mandate" or "NACH-". Acceptance harness for this rule: the review-157 messages, zero money-to-notice changes.
- capture/parsers balance and limit (ticket 156, parser version 5): `extract/balance.ts` (`readBalance`, `readAvailableLimit`, and `findBalance`/`findAvailableLimit` for the figure alone) puts `balanceMinor` and `availableLimitMinor` (paise) on a money parse, through the overridable `balance()` and `availableLimit()` steps of `BankParser` (no bank overrides them yet) and the IDFC card-spend format. Only the first labelled figure in rupees is kept. Left out: masked, negative, `(-)`, `Dr`, `(Dr)` or a `-` glued after it at the end or before punctuation (`-SBI` and `- HDFC Bank` are a signature, `:-` a separator), foreign, garbled grouping, at least 1e13 paise; a rule or warning, also with a word before Bal ("Min Avl Bal", "Insufficient Avl Bal", "Average Balance"); money that is not the account's (outstanding, total or current balance, loan, principal, EMI, wallet, UPI Lite, cashback, FASTag, NCMC, card, reward or loyalty points; a whole word vetoes only when a space follows it, so a word ending the sentence before ("for Loan EMI. Avl Bal") does not, and only short forms take a dot: "Min. Avl Bal"); money still to move ("will be", "to be", "due" but not "due to", "payable" after it); a daily, cash, ATM, UPI or per-transaction limit; a bare "Bal" with no currency. `base.ts` keeps a figure only for the account in last4: printed next to other masked digits in the same clause ("A/c XX9999 Avl Bal", not across a sentence end and not out of a reference like "631800XX1234") it is dropped (a 3-digit ICICI mask matches by its end), a card bill payment keeps no balance (either account's), and a limit is kept only on a card read (the bank-account side of a card payment, where `KnownBankParser` blanks the digits, drops it). They add no confidence, are never the amount, are stored only through `parse.fields`, and are not in the review API (`serializeCapture` lists its fields one by one). Nothing uses them yet; they are real money figures, so never log them.

- Ticket 177 shared fixes: a bank's shape bonus is added only when the parse names an account (`base.ts`), so a no-account read never reaches 0.8 where a categorise rule could book it; a debit the same message says came back or was undone (`MONEY_UNDONE` in extract/direction.ts: reversal, refund, reimbursement, chargeback, cancelled, voided, bounced, returned, rolled back, adjusted back, re-credited, credited back; never bare "credit"/"Cr") stays in Review for every parser, generic included, the word counting anywhere, even in a shop's name (a captured name could swallow it, so "REFUND KITCHEN" goes to Review as accepted noise) (`base.ts`), while a refund or reversal credit on its own is still booked; "… using (your) credit card" is a spend, never a card bill payment, under every bank parser; "<bank> Credit Card XX#### credited" is a card payment in the generic parser too (`isCardPayment`); `ignore.ts` drops a transaction "has been / is declined" only when that is said in the sentence holding the amount, and never when money came back; a card spend written with no money verb ("Thank you for using … Card … for INR 845.00", "used your card … for Rs", `CARD_USE` in extract/direction.ts) counts as money moved in `ignore.ts` (a help line about failed txns or a refund still to come never drops it) and as an expense in `findDirection`; a line break ends a merchant and help words (get, call, report, dispute, block) never start one; `vpaAfter` drops a trailing ".Ref"/".Avl"/".Bal"; `ACCOUNT_LIKE` also rejects single-X masks and masks inside a number. account-match.ts knows every phase 8 and 9 bank (`BANKS`: parsed name, account-name aliases, SMS header; `banksInName` takes the longest bank name in a name, so "State Bank of India" is never Bank of India and "City Union Bank" never Union Bank) and matches a three-digit mask by suffix only with a known bank and the right kind, preferring the bank's own account (see docs/reconcile.md). A declined attempt with no money verb is ignored; with a money verb it is capped at 0.5 (`txnDidNotGoThrough`); a card use whose transaction did not go through is dropped and a "scheduled" one stays a reminder; `isCardUse` needs a card mask or "at <shop>" (no thank-you promos). A card bill paid with a debit card is a card payment; only "using … credit card" makes a payment a spend. The generic parser also reads a card bill paid from an account ("debited … towards <bank> Credit Card XX2614", "… towards credit card bill", a next sentence "Towards/Paid to … Credit Card XX…", "Credit Card Payment XX…") as a card payment, and a card payment keeps only a card's own digits, never the paying account's (`base.ts`). `findLast4` skips masks after ref/RRN/UTR; help phrases (not single words) never start a merchant, nor a card or "<bank>-<digits>".
- capture/parsers/banks (version 4, ticket 155): HDFC (`HDFCBK`), ICICI (`ICICIB`, `ICICIT`), SBI (`SBIINB`, `SBIUPI`, `ATMSBI`, `CBSSBI`, `SBICRD`), Axis (`AXISBK`), Kotak (`KOTAKB`, `KOTAKD`) and IDFC FIRST (`IDFCFB`, `IDFCBK`), each with its app package. Only headers that carry the bank's own name are listed: a wrong header would route another bank's messages (`KBANKT`, likely Karnataka Bank, is deliberately absent). They extend `KnownBankParser` (banks/known.ts), which collapses whitespace first and keeps every capture bounded (no catastrophic backtracking; a 5,000-character padded message parses in a few ms). The 0.05 bonus comes only from one of the bank's own `shapes` (`confidenceBonusFor`), never the sender alone. A read stays at or under 0.75 (Review) when money has not moved yet (refund or reversal initiated, "will be credited", "will reflect", "in 5-7 days"), when money moved while a mandate was set up or a credit names a mandate (a mandate's own notice never reaches a bank parser, and a debit made under a mandate is booked like any debit; ticket 157), or when it has both a debit and a credit word and is not one of the bank's shapes. Money paid to a credit card ("to <bank> Credit Card", "; <bank> Credit Card XX credited", "towards ... credit card", "CREDIT CARD BILL PAYMENT", "Card ... payment of ... received", ICICI `InfoBIL*... Card`) is `cardPayment` (cap 0.5), tested only on the sentence holding the amount and the one right after it when that names a card by its masked digits ("Credit Card XX6047", "card ending 6047"), has no amount and is not a promo line (Pay, Earn, Convert, Use, Get, Click, Download) (`moneySentence`); "Credit Card Payment" with or without "bill" counts, never on a spend or a refund, and "Credit Card Services" (a business name) is not a card. Paid from the person's bank account, it keeps type income like every card payment (ingest queues it as `card_payment`) and carries only the card's own digits, never the debited account's (a card found as the account, "Your HDFC Bank Credit Card 5150 payment of ...", is kept), so it never suggests the wrong account. An ATM parse never keeps a merchant. A masked number ("XX4410"), an account or an amount is never a merchant. ICICI masks accounts to three digits, so its `last4` can be 3 digits: it never equals a saved 4-digit `smsLastFour`, and account-match then falls back to the bank-and-kind guess exactly as for a message whose digits are not saved, so it cannot pick a wrong account by digits; `learnDigitsFromCapture` only learns 4 (follow-up: match 3 digits against the end of saved digits). Axis never takes the `SMS BLOCKCARD XX1234` digits as the account. SBI reads "done at" as a debit only in its card-spend shapes ("by SBI Debit Card 1234 done at", "done at SHOP on your SBI Credit Card ending"), never for a deposit or a credit.
- capture/parsers (version 3, ticket 150): a fraud warning ("never share OTP") is removed before the OTP check, so a real debit carrying it is kept; a failed or declined payment is ignored unless money came back ("reversed", "credited"); a spend in another currency keeps its currency (`currency`, e.g. USD) and a limit ("Avl Lmt") is never the amount; a card bill payment is `cardPayment: true`; "debit" as a noun (not "debit card"), WDL and Dr/Cr before an amount count as direction; a phone or account number is never the merchant and a VPA keeps its dots; an EMI takes the account the money left, not the loan a/c.
- capture/ingest.ts: a parse in another currency queues as `foreign_currency` (Review shows no rupee amount; the person enters what the bank billed) and a card bill payment as `card_payment`; neither is ever auto-created. Both are queued before cross-channel matching (a foreign parse has no `eventKey`), so a notification and an SMS of the same spend abroad or bill payment show as two Review items; resolving one and removing the other is up to the person.
- capture/ingest.ts: an ATM withdrawal parse (`atm: true` from `parseCapture`) with a live cash account is created as a transfer to cash, not an expense; `handleMatch` never rewrites that transfer from a later message.

## Rules and gotchas
- Household sharing never changes how an existing query is scoped: every current route still filters by `user`. New shared reads must go through `loadActiveShare` and the share's account ids, return a field whitelist (never the raw document), and answer 404, not 403, for anything the caller may not see; a share is never cached. No realtime resource streams shared data. `createTransaction` skips the owner's goal round-up for a row with `provenance.addedBy` (a household editor's); the editor write re-reads the live share right before it writes.
- budget-service and goal-service own create, update and soft delete; the browser `[id]` routes and the integration `[id]` routes both call them.
- transfer-service owns transfer edit (amount, accounts, date: balances fixed in one pass); create and delete call transaction-service. A transfer row is never income or spending.
- subscription-service never stores detections, only the user's choice per merchant and cadence (`SubscriptionDecision`); it leaves out recurring series the user already tracks (`isRecurring`).
- tax-service answers `currency` and `exponent` (the base currency, `minorExponent`), writes CSV amounts with `minorToMajor` under an `amount (CODE)` header, and the `/tax` page formats with money-format.ts `formatMinor` (utils.ts `formatCurrency` assumes 2 decimals). It sums only the stored base `amount`, never `originalAmount`; a split line is its own row and counts once.
- tax-service counts income and spending only: no transfers (an ATM withdrawal is one only with a cash account), voided or deleted rows, recurring instalments once paid. A confirmed refund comes off spending in the year it arrived (cash basis, the refund's own date), is skipped when its original is voided or deleted, and is deductible as its original is (this user's expenses read by id in chunks of 1000 after the year's refunds are grouped, no `$lookup`). Known limit: a refund links to one split line, so for a split purchase deductibility comes from that line only, not the whole group. Category names are compared with `categoryKey` in JS on both sides, never Mongo `$toLower` (ASCII only). `availableYears` reads only the first and last rows (`yearRangeReads`; `isDeleted` matched as `$in [false, null]` so the date indexes give the order; the first and last `date` over all counted rows plus the first and last `paidAt`, so the list never misses a year but may offer one with no counted row when a scheduled date is far from the paid date). Refund groups are never cut short. Settings change by `changeTaxCategories` (atomic add and remove, 50 name cap). csv.ts leaves a real number alone, so a negative amount stays numeric, while text starting with a formula character is quoted.
- A confirmed refund (`refundStatus: confirmed` income row) is netted out in stats-service, budget-service and budget-alert; a new aggregation over income or expense must do the same.
- rule-service owns categorise rules; createTransaction() and capture/ingest.ts call it, the browser and integration rule routes call it. Rules are not a realtime resource.
- loan-service owns loan create, update, delete and repayments; the browser and integration loan routes both call it.
- Put logic here, not in routes. transaction-service, loan-service, goal-service, budget-service and stats-service exist so web and integration routes cannot drift.
- No mongoose sessions anywhere; multi-step writes are sequential.
- `appendLedgerBlock` (ledger.ts) writes a per-user hash chain (`sequence`, `previousHash`, `hash`); concurrent appends retry up to 25 times on the unique {user, sequence} index.
- Redis and the TTL caches are optional or per instance; code must work without them.
- A split is one Transaction row per line, so stats and budgets need no split logic; keep it that way. Only split lines through split-service/createTransaction.
- split-service edits the lines in ONE Mongo transaction (`session.withTransaction`; production is a replica set, tests use `MongoMemoryReplSet`): rows, new rows and receipt moves commit or abort together, two edits at once serialise on the first line (write conflict, retried), ledger blocks are written after the commit. Receipts of removed lines move to the first line (cap checked in the same update) before the line is deleted. Other code stays free of sessions.
- Receipt cascade (`deleteReceiptsOfTransactions`) runs AFTER the delete/void/cancel, retries once, then logs; `getReceiptImage` checks the parent, quota counts only live parents, and `sweepOrphanReceipts` (on list and add) purges leftovers. Account self-delete purges receipts as its last step; `/api/me/export` lists their metadata only.
- Receipts: never return a receipt URL or bytes without `getReceiptImage(userId, id)`; a receipt is deleted with its transaction (`deleteReceiptsOfTransaction` in `deleteTransaction`). The key is `CAPTURE_ENCRYPTION_KEY` with the purpose `receipt`: changing that env value makes stored receipts unreadable.
- capture/ingest.ts reads `CAPTURE_ENCRYPTION_KEY`; log-security.ts reads `TOTP_ENCRYPTION_KEY`.
- integrations/sms-parser.ts (`parseBankSms`) has no importer in src, scripts or server.ts; ingest uses `parseCapture` from capture/parsers.
