# Encrypted backup and restore

A private copy of one person's data that they can keep anywhere and restore after a phone change or a server move. Integration routes only (`/api/integrations/backup`, `/api/integrations/backup/restore`); API contract in [api-contracts.md](api-contracts.md#backup-and-restore).

## Threat model

| Threat | What stops it |
| --- | --- |
| Someone gets the backup file (cloud drive, shared phone, email) | AES-256-GCM under a key from the person's passphrase (scrypt, N=131072, r=8, p=1, 128 MiB of memory per derivation, random 16 byte salt, random 12 byte IV). Nothing readable in the file besides the format, version, time it was made and the KDF settings. The passphrase is the only protection: at least 12 characters is enforced, a few random words is better, and a stolen file can be guessed against offline (roughly a third of a second per try on one core). There is no recovery if the passphrase is lost |
| The file is changed (or a different file is swapped in) | GCM tag over the ciphertext, and the header (format, version, time, KDF cost, salt, IV) is bound to it as additional data. A wrong passphrase, a flipped bit anywhere and a changed header all give the same answer (`reason: unreadable`), so the server is not a guessing oracle for which part was wrong |
| A hostile file sent to restore | The body is counted as it streams in and cut off past a cap of 3,000,000 bytes of encrypted data (about 4 MB as base64: what `POST /backup` can produce, and under Vercel's 4.5 MB request limit), at most four bodies are read at once per server process and one at a time per person, each with a deadline (90 seconds in total, 15 seconds without a new chunk; a read that runs out is cancelled without waiting for the cancel to finish), a missing or false Content-Length does not help the KDF cost must equal exactly the one the file's version allows (a file cannot ask for a huge cost), the unpacked text is capped at 48 MiB (compression bomb), every field is checked by a strict whitelist schema (types, lengths, enums, money range, `http(s)` links only, list caps), unknown fields and any `user`, role or `deletedBy` in the file are dropped, a reference to a row that is not in the file rejects the whole file |
| Restore used to touch another person's data | Every restored row is owned by the caller; the file's ids are only used if no row has them, and a row id held by someone else gets a fresh id. Nothing is updated or deleted, so no other user's row can be overwritten |
| Restore used to wipe or corrupt your own data | Merge only: rows already there (same id, or same budget month and category, rule or subscription choice) are kept as they are and skipped. There is no replace mode. A dry run shows the counts first and writes nothing |
| Secrets leaking into a backup | Left out by construction (the export is a whitelist): API keys, sessions, the password hash, push subscriptions, raw captured messages, notifications, the hash-chained ledger, card statements and net worth history. A backup never contains `CAPTURE_ENCRYPTION_KEY`. The server does use it for two things here: the ids restore derives, and (outside backup) the encryption of receipts. Changing it makes a re-run of an old restore add copies and makes stored receipts unreadable, so keep it the same across deploys and server moves |
| Guessing the passphrase through the API | Hard limits per person per 10 minutes, counted atomically: 40 requests (checked before the body is read). The key gate covers whole jobs (database reads, compression and key derivation), two at a time per server process, with a queue of four whose waiters give up after 10 seconds (429 `busy`) and a 50 second limit on a job (500 `timeout`, below the platform's maximum duration, so a stalled database call cannot pin a slot for everyone; the work itself is abandoned, not killed). A slot is taken before any database or compression work starts, so a busy server answers first; a call turned away as busy before that point gets its counts back, and nothing is ever given back once work has started. Refusals caused by the caller (too large, a bad passphrase or file) keep the request count; a read `timeout` or `busy` is the server's or a slow link's doing and gives the request slot back, 6 exports, 12 real restores and 30 dry runs (a dry run never uses up the restores) on top of the normal per-key limit; at most two key derivations at once per server process, a queue of four behind them, and a 429 (`reason: busy`) beyond that, answered before the body is read |
| The passphrase leaking from the server | Sent in the POST body only (never in a URL), used for one call, never stored, never logged (the route logger records route and status only), not part of the idempotency fingerprint |

Out of scope: someone who has the person's API key and passphrase is the person; a compromised server sees data in the clear while it builds or opens a backup.

## Format

A JSON file. New files are version 2; version 1 (scrypt N=65536, made before the cost went up) still opens, because its lower cost stays on the whitelist, so an older backup restores. A file cannot mix the two (a version 1 header with the version 2 cost is refused). Shape:

```
{ "format": "expense-tracker-backup", "v": 2, "createdAt": ISO,
  "kdf": {"name": "scrypt", "N": 131072, "r": 8, "p": 1, "salt": base64(16)},
  "cipher": {"name": "aes-256-gcm", "iv": base64(12), "tag": base64(16)},
  "ciphertext": base64 }
```

The plain text is gzip of `{app: "expense-tracker", version: 1, createdAt, data}`. `data` has `accounts`, `transactions`, `budgets`, `goals`, `loans`, `repayments`, `rules`, `sinkingFunds`, `subscriptionDecisions`, `manualAssets`, `envelopePlans` (an additive list: the payload stays version 2, an older app or server that does not know it drops it silently and a file from before it reads as no plans; a file in a base that is not two-decimal is refused as a whole, plans included, like any other row; one per month: income and the amount per envelope; the move history is not kept; a month the person already has a plan for is left alone; the on or off setting is a preference and stays on the account) and `spendLimit` (one or null). Next to `data` the file carries `baseCurrency` (the currency of every amount in it) and `tax.deductibleCategories` (the person's tax settings). Money fields are validated: every currency code must be one the app supports, a foreign amount is all or none of `originalAmount` (at least 1), `originalCurrency`, `originalExponent` (that currency's digits) and `rate` (`rateDate` and `rateSource` only with them; a client rate has no date). Payload version 2 (the file envelope has its own version, `v`, which stays 2) added `baseCurrency`, the foreign-currency originals on a transaction (`originalAmount`, `originalCurrency`, `originalExponent`, `rate`, `rateDate`, `rateSource`), the per-row tax flag `deductible` and `tax`; version 1 files still read (all are optional there). Soft deleted rows are not included, except soft deleted accounts: they go in (still marked deleted) because live balances include transfers to and from them and their transactions need something to belong to. Amounts stay integer paise. Rows are written by `id`, with references by id.

## Restore rules

- Ids: a row keeps the file's id when no row has it. If someone else holds it, the row gets an id that is an HMAC of (the caller, the kind of row, the file's id, an attempt number) under a server-only subkey of `CAPTURE_ENCRYPTION_KEY` (no new setting). It is the same every time, so running the same restore again finds those rows and skips them instead of copying them, and nobody without the server secret can work it out to plant a row on it. If that id is somehow held by another person, the next attempt number is used (the order is fixed, so a re-run lands on the same id). Changing `CAPTURE_ENCRYPTION_KEY` changes the derived ids, so a re-run after that would add copies. A recurring series or split group id that another person's rows already use is replaced the same way (and checked against other people's rows too), so a restored row never joins a series that is not the caller's; the monthly top-up of open-ended series is also scoped to one person's rows.
- Rows that already exist here and sit in the trash (soft deleted) count as existing and are skipped, not brought back; the report says `N rows in the backup already exist in your trash and were not restored.`
- Order: accounts, loans, goals, budgets, rules, funds, assets, subscription choices, transactions, repayments, so every reference points at a row that exists.
- Rows are inserted directly, not replayed through the services: balances and remaining amounts come back exactly as they were in the file. If a transaction is added to an account that already exists here (a merge, not a new phone), that account's balance is not recalculated; the response says so in `warnings`.
- A restore is not one transaction (the app has no database transactions). If it stops half way, run it again: rows already written are kept and skipped, and the rest are added.
- Receipts are not in a backup. A transaction's `attachments` hold receipt ids, so the field is neither exported nor restored (an older file's `attachments` are ignored). The export answer says how many receipts were left out (`warnings`); the photos stay on the server.
- Base currency: every amount is in the base currency, so a file is only restored into the same base. A file in another base is refused with `400 BASE_CURRENCY_MISMATCH` once the person has money data (or the base is locked); a dry run reports the same refusal. With no money data yet the base is set from the file (a warning says so), but only when the restore actually writes something; a file with only settings sets and locks nothing. The base is locked before any amount is inserted. The base is only ever a two-decimal currency (the rest of the server reads base amounts as hundredths): a file whose base is not, and differs from the person's, is refused with `400 BASE_CURRENCY_ONLY_TWO_DECIMALS` (dry run included); a person whose own base is such a legacy one (JPY, KWD) gets the same refusal when the restore would write rows, since the transaction and import paths refuse them too, and a restore that writes nothing is still fine. If setting the base fails the answer carries the real reason, not the "amounts stored" text. Version 2 files always record `baseCurrency` (one without it is `invalid`). A version 1 file never recorded it, so its base is unknown: it is never used to set the base, and it is only restored into an account whose base is INR (what such files held before other bases existed), with a warning; any other base gets `400 BASE_CURRENCY_UNKNOWN`. Every restored transaction is labelled with the file's base (a transaction labelled otherwise makes the file `invalid`); budgets, goals, loans and funds are relabelled the same way, and an account keeps its own currency label. The export writes the base on every transaction.
- Tax categories: `deductibleCategories` are restored only when the person has none; otherwise they are kept and a warning says so.
- Tags: the server's own link tags (`loan:`, `repayment:`, `credit_statement:`, `loan_principal`) name ids that are remapped on restore, so they are dropped; the person's tags stay. Loans and repayments come back as rows, but a repayment's link to its transaction and loan is not rebuilt.
- The restore route may run 60 s (`maxDuration`; the gate cuts a job at 50 s) and keeps its pending idempotency record 120 s, like the import commit. Budgets, rules and subscription choices are placed like every other kind (same owner check, derived ids with the attempt number, trash), and then checked against the person's own unique key, so a re-run, or a run racing a timed out one, cannot add copies; one that sits in the trash is counted as not restored, with the trash warning.
- Restored rows do not enter the audit ledger (`/api/logs/ledger`), which only records writes made through the app.
- Limits: 1,000 accounts, 50,000 transactions, 50,000 repayments, 20,000 budgets, 5,000 loans and subscription choices, 2,000 goals and rules, 1,000 funds and assets. A person above a limit cannot make a backup until we raise it (the error says which). Vercel Functions accept at most 4.5 MB of request body and send at most 4.5 MB of response body ([limits](https://vercel.com/docs/functions/limitations)). So a large restore needs the self-hosted server, and `POST /backup` refuses, before encrypting, a backup whose answer (the packed data as base64 plus the envelope) would pass about 4 MB: `413 TOO_LARGE_FOR_RESPONSE` with a message pointing at the CSV export.

Code: `src/lib/backup-crypto.ts` (format, KDF, cipher), `src/lib/backup-service.ts` (what is exported, the schemas, restore), `src/lib/integrations/backup-http.ts` (bounded body, rate limit), routes under `src/app/api/integrations/backup/`. Tests: `src/test/backup.test.ts`.
